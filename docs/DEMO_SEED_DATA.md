# Demo MSP seed data (`demo-msp`)

Synthetic, **tenant-scoped** data for the **`demo-msp`** workspace. All companies, people, and situations are **fictional** (UK-style names and industries for realism). Nothing is copied from real customers.

## Seed data classification (current)

| Class | Current status |
|------|----------------|
| Structural/app-required | Seeded directly (tenant/users/roles/memberships/onboarding/plans/subscription). |
| Prompt/config seed | Seeded directly (platform prompt catalog, AI provider catalog, default tenant AI provider/routes from env defaults). |
| Demo business/customer data | **Not seeded directly** in runtime demo seed. |
| Connector-backed demo data | Populated by connector syncs from Connector Lab (M365 currently wired with mapping-review states). |
| Legacy direct connector-like data | None in runtime seed for demo tenant. |

## What gets replaced

On every `seed_all` run (`python -m app.db.seed` or Docker entrypoint seed), for **`tenants.slug = demo-msp`** only:

- **Deleted** for that tenant: connector/business telemetry rows including customers, contacts, tickets, opportunities, quotes, recommendations/actions/scores, mapping reviews, source mappings, sync runs, and connector connection rows.
- **Recreated**: structural connector connection rows pointing to Connector Lab (Autotask, ITQuoter, Xero, M365, Veeam, 3CX) with safe dev config.
- No synthetic customer or business telemetry rows are seeded directly.

**Not** wiped: users, memberships, plans, subscriptions, onboarding state, AI providers (a default provider row is ensured from env defaults if missing), prompt definitions, tenant AI routes.

Other tenants are untouched.

## Reseed / reset

1. **Full DB reset** (wiping all tenants): `docker compose down -v` then `docker compose up --build -d` (destructive).
2. **Reseed only** (keeps DB, reapplies seed including demo workspace replace):  
   `docker compose exec backend python -m app.db.seed`

Requires migration **`0012_customer_demo_profile`** applied (`alembic upgrade head` — normally automatic on backend container start).

## Preferred demo flow (connector-first)

1. Seed structural/config baseline: `docker compose exec backend python -m app.db.seed`
2. Run connector syncs for connector-backed slices (from `/app/integrations` or API):
   - **M365**: `POST /api/v1/integrations/connections/{m365_connection_id}/sync`
   - **Autotask PSA** (Connector Lab): sync the Autotask connection after M365 baseline exists so accounts can map to canonical customers; contacts/tickets/opportunities/quotes import for mapped accounts.
3. Open `/app/integrations/mappings` and use first-run baseline actions:
   - **Create customers from all eligible rows** (or selected rows) when starting from zero/low canonical customers.
   - Then use accept/reject/remap/unlink for remaining uncertain rows.
4. Verify `/app/customers` now shows imported canonical customers. (Playwright **`frontend/e2e/global-setup.ts`** can trigger a **Microsoft 365 (Connector Lab)** sync when no customers exist yet — see **[DEVELOPMENT.md](DEVELOPMENT.md#playwright-browser-smoke-review--qbr)**.)
5. Verify `/app/m365-health` shows linked posture rows for confirmed/imported mappings.
6. Product surfaces read canonical rows generated by confirmed mappings/syncs.

M365 is the primary identity/hygiene slice; **Autotask** supplies service/commercial rows once accounts align to canonical customers (see `AutotaskConnectorAdapter`). High-confidence mappings may be auto-confirmed; fuzzy/unmatched source records stay reviewable in Mapping Review instead of being silently auto-created as canonical customers.

Connector Lab M365 vendor payloads are Graph-inspired (`organization`, `users`, `subscribedSkus`, `licenseDetails`) and do not include MSPIntel-only control fields. Mapping scenario metadata is available separately via Connector Lab dev-only scenario views/endpoints.

## Assumptions

- **No live customer systems** are called in demo seed or Connector Lab flow.
- Connector Lab is the preferred source for realistic connector-backed demo telemetry when that slice is implemented.
- Runtime demo seed intentionally does not create direct fake business telemetry.
- Practical thin-slice flow is now: M365 sync + mapping import (customer baseline) -> Autotask sync (accounts + contacts/tickets/opportunities/quotes) -> Customer 360 + AI AM guidance from connector-sourced context.
